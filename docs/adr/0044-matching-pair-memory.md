# ADR 0044 — 매칭은 페어를 객체로 모아 두지 않는다

- 상태: Accepted (2026-10-18)
- 근거: measurement (#294)

## Context

1:1과 그룹 매칭 모두 참여자의 모든 페어 점수를 계산한다. 페어 수는 인원의 제곱이다.

- 1:1은 자격 페어를 전부 `ScoredMatch` 리스트로 모은 뒤, 회원마다 리스트를 하나씩 더 만들어 섞고 정렬했다.
- 그룹은 페어 점수를 `Map<Long, Map<Long, Double>>`에 양방향으로 담았다. 박싱된 키·값과 해시 노드 때문에 페어당 150바이트 안팎이다.

테스트 JVM(힙 512MB)에서 답 10문항, 남녀 반반으로 재 보니 2,000명에서 1:1이 최대 약 380MB, 그룹이 약 540MB를 썼고 3,000명에서는 둘 다 OOM이 났다. 운영 ECS는 `-Xmx`가 없어 힙이 약 256MB라 퀴즈셋 하나에 1,000명대부터 위험하다(추정).

힙을 늘리는 것만으로는 막을 수 없다. 그룹은 5,000명이면 수 GB가 필요하고(추정), 태스크 메모리 1024MB에서 최대 사용률이 이미 약 68%라 힙을 키울 여유도 적다.

## Decision

페어를 객체로 모아 두지 않는다.

- 1:1은 자격 페어를 `Sequence`로 하나씩 만들고, `TopPicksSelector`가 회원마다 크기 5짜리 힙만 유지한다. 선발 규칙([ADR 0040](0040-one-to-one-top-picks-per-member.md))과 결과 순서는 그대로다.
- 동점은 페어를 만들 때 무작위 값을 하나 붙여 그 값으로 자른다. 전에는 회원마다 후보를 섞은 뒤 stable 정렬했는데, 다 모으지 않으면 섞을 수 없다. 회원 한 명 기준으로 동점끼리 고르게 무작위인 것은 같다([ADR 0007](0007-matching-pure-pipeline.md)).
- 어드민의 "후보가 없는 이유"는 점수 없이 자격 상대가 있는 회원 id만 구한다(`findMemberIdsWithEligiblePair`).
- 그룹은 페어 점수를 `DoubleArray` 하나에 한쪽 방향만 담는다. 회원 id는 순번 맵으로 바꿔 찾는다. 값을 그대로 저장하므로 점수와 분할 결과는 바뀌지 않는다.

## Consequences

- 얻음: 같은 측정에서 5,000명이 1:1 최대 약 180MB, 그룹 약 200MB로 끝났다. 이 값에는 GC가 아직 치우지 않은 쓰레기도 섞여 있다. 계속 들고 있는 것은 1:1이 회원당 5개, 그룹이 페어당 8바이트(5,000명에 약 100MB)다.
- 비용: 계산 시간은 여전히 인원 제곱 이상으로 는다. 5,000명이면 1:1 약 1.4초, 그룹 약 39초였다. 후보 생성은 퀴즈셋마다 트랜잭션 하나라 그동안 DB 커넥션을 잡고 있다.
- 후속: ECS 힙 설정은 따로 정한다. 그룹이 1만 명을 넘으면 배열도 400MB가 되므로 점수를 더 작은 타입에 담거나 계산 방식을 바꿔야 한다.
