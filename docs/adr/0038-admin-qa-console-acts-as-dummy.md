# ADR 0038 — 어드민 QA 콘솔은 앱 API 컨트롤러를 더미 principal 로 그대로 호출한다

- 상태: Accepted (2026-10-04)
- 근거: discussion (#246)

## Context

채팅 QA는 상대가 있어야 한다. 1:1은 신청을 받아 줄 사람, 그룹은 3명의 수락이 있어야 방이 열리고, 방이 열려도 상대 메시지·읽음 숫자·이탈·투표를 혼자서는 볼 수 없다. 어드민 더미 회원은 소셜 계정이 없어 로그인할 수 없으므로 아무 행동도 못 했다.

두 방법을 놓고 골랐다.

- **더미 계정으로 로그인**: 어드민이 더미의 토큰을 발급해 FE에 넘긴다. 서버 코드는 엔드포인트 하나지만 사실상 계정 전환 기능이고, 배포 환경이 `prod` 프로필 하나라 local 전용으로 막을 수 없다. 그룹 QA는 브라우저 프로필을 3~4개 띄워야 한다.
- **어드민이 더미를 대신 움직이기**: 어드민 화면의 버튼이 더미의 행동을 실행한다. 인증을 건드리지 않고 테스트 폰 하나로 그룹까지 확인할 수 있다. 기능마다 버튼을 만들어야 한다.

대신 움직이기를 고른 뒤에도 실행 방식이 둘이었다. 수락·종료·나가기·투표는 STOMP 브로드캐스트·알림·평가 열기를 서비스가 아니라 **컨트롤러가 커밋 뒤에** 한다(`ChatController.leave`, `PersonalMatchController.acceptMatch` 등). 어드민이 서비스만 부르면 이 후처리를 어드민에 다시 적어야 하고, 실제 경로와 어긋나는 순간 QA 결과를 믿을 수 없게 된다.

## Decision

어드민 QA 콘솔(`/admin/qa/**`)은 **앱이 부르는 API 컨트롤러 메서드를 더미의 `MemberPrincipal`로 그대로 호출한다.** STOMP 전송은 `ChatStompController.sendMessage`에 앱 연결과 같은 모양의 `Authentication`을 넘긴다.

- 대상은 더미(`dummy-` 닉네임)만이다(`QaDummies.principalOf`). `NicknamePolicy`가 `-`를 허용하지 않아 실회원은 이 접두어를 가질 수 없다.
- 앱이 받는 거부(`WarnException`)는 삼키지 않고 코드와 함께 화면에 보여준다. QA 중에는 그 거부 자체가 확인할 대상이다.
- 조회는 앱 API를 쓰지 않고 저장소를 직접 읽는다. 어드민은 방 멤버가 아니고, 나간 사람의 커서까지 한 화면에 보여야 한다. 투표 집계만은 규칙(활성 멤버 기준)을 다시 만들지 않으려고 `ChatVoteService.getVotes`를 방 멤버 한 명의 눈으로 부른다.
- 더미를 지울 때 더미가 낀 채팅방·1:1 매칭·그룹은 통째로, 그것을 가리키는 실회원 알림·평가·재매칭까지 지운다(`DummyDataCleaner`). QA로 만든 방은 일회용이고, 외래키가 없어 회원만 지우면 나머지 행이 사라진 회원을 가리킨 채 남는다. 알림이 무엇을 가리키는지는 `NotificationType.target`으로 판단한다.

## Consequences

- 얻음: 브로드캐스트·알림·평가 열기·잠금 순서가 앱 경로와 같아 QA 결과를 그대로 믿을 수 있다. 컨트롤러 시그니처가 바뀌면 콘솔이 컴파일 에러로 드러난다. 인증 구조를 건드리지 않았다.
- 비용: 어드민 패키지가 API 컨트롤러에 의존한다(계층이 깔끔하지 않다). 앱에 새 채팅 동작이 생기면 콘솔 버튼을 따로 추가해야 한다. 더미 정리가 같은 방에 있던 실회원의 데이터까지 지우므로, 실사용자가 더미와 매칭될 수 있는 시기에는 정리 버튼을 쓰면 안 된다.
- 후속/연쇄: 상대(더미) 쪽 FE 화면은 이 방식으로 확인할 수 없다. 필요해지면 더미 로그인 방식을 별도 ADR로 검토한다.
