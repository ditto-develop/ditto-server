# ADR 0018 — 알림은 문구를 확정해 적재하고, 적재는 비즈니스 트랜잭션을 되돌리지 않는다

- 상태: Accepted
- 근거: Issue #136, 피그마 `7.2 알림 센터`(`2499:36308`)·`7.1 신고 & 알림` 스펙 표(`676:15297`)

## Context

알림 센터 화면이 필요한 것은 목록·읽음 API지만, 목록을 채우는 쪽에서 결정할 것이 셋 있었다.

1. **문구를 누가 만드는가.** 채팅 SYSTEM 메시지는 반대로 정해져 있다 — `content`에 사건 코드(`USER_LEFT`)만 넣고 표시 문구는 클라이언트가 만든다(`docs/domains/chat.md`). 같은 규칙을 알림에 쓰면 유형+파라미터를 저장하고 클라이언트가 렌더한다.
2. **적재를 어느 트랜잭션에 넣는가.** 적재 지점 여섯 곳 중 넷이 매칭 배치·그룹 참여·채팅 전송·평가 열기처럼 사용자가 결과를 기다리는 경로다.
3. **같은 사건이 반복될 때 무엇을 하는가.** 스케줄러는 매 주기(1분) 같은 방을 다시 집어오고, 새 메시지는 방 하나에서 수십 번 온다.

## Decision

**문구는 서버가 발송 시점에 확정해 저장한다.** `notification.title`·`body`는 스냅샷이다.

- 곧 붙을 푸시(FCM)와 센터가 같은 문구여야 한다. 클라이언트 렌더 방식이면 문구가 두 곳(푸시 페이로드·앱)에 갈라진다.
- 센터는 "그때 무엇을 알렸는가"의 기록이다. 닉네임이 바뀐 뒤 다시 렌더하면 사실이 달라진다.
- 채팅 SYSTEM 메시지와 반대인 이유는 그쪽은 **보는 사람에 따라 문구가 달라지는** 사건이기 때문이다(나간 본인에게 "상대방이 종료했습니다"는 거짓). 알림은 수신자별로 행이 따로 있어 그 문제가 없다.

문구는 `NotificationMessages` 한곳에 모은다(정본은 기획의 "알림 문구 정책" 문서).

**적재는 `REQUIRES_NEW`로 분리하고 실패를 삼킨다.** `NotificationAppender`(입구, 트랜잭션 없음, 실패 흡수) → `NotificationWriter`(`REQUIRES_NEW`, 저장). 두 빈으로 나눈 것은 자기 호출이 프록시를 지나지 않기 때문이고, 호출자 트랜잭션에 참여하면 적재 실패가 그 트랜잭션을 rollback-only 로 만들어 예외를 잡아도 커밋이 깨지기 때문이다.

**중복 정책은 유형이 정한다**(`NotificationType.duplicatePolicy`).

- `ONCE_PER_TARGET` — `(회원, 유형, 대상)` 존재 검사로 막는다. **알림 행 자체가 처리 완료 표시**라 별도 플래그·outbox 가 없다(`RematchChatRoomOpener`·`EndedChatReviewOpener`와 같은 수렴 루프).
- `COLLAPSE_UNREAD` — 새 메시지 전용. 같은 방의 **안읽은** 행을 지우고 다시 삽입한다.

**접기는 갱신이 아니라 삭제+재삽입이다.** 기존 행의 문구만 갱신하면 오래된 `id`에 최신 시각이 붙어 `id` 정렬(= 시간 정렬)이 깨지고, 커서 페이징이 `(created_at, id)` 두 키를 다뤄야 한다.

**보관·조회 창은 30일 하나다.** 스펙 표의 "최근 30일"을 조회 필터로 쓰고, 같은 기준으로 purge 배치가 지운다.

## Consequences

- **롤백된 작업의 알림이 드물게 남을 수 있다.** 적재가 먼저 커밋되기 때문이다. 알림은 읽기 전용 통지라 이 방향의 오류를 감수한다 — 반대 방향(알림 적재 실패로 매칭·채팅이 취소됨)이 훨씬 나쁘다. 스케줄러가 부르는 지점은 전이가 커밋된 뒤에 부르므로 이 창이 아예 없고, 트랜잭션 안에서 부르는 곳은 `GroupMatchService` 하나다.
- **문구를 바꿔도 과거 알림은 낡은 문구를 유지한다.** 기록으로서는 옳지만, 오타를 고쳐도 이미 나간 알림은 그대로다. 마이그레이션이 필요하면 별도 작업이다.
- **닉네임 변경이 과거 알림에 반영되지 않는다.** 같은 이유로 의도된 결과다.
- **`(member_id, type, target_id)`에 유일 제약을 두지 않는다.** 새 메시지는 읽은 뒤 다시 오면 새 행이어야 해서 DB 제약으로 표현할 수 없다(부분 유일 인덱스가 MySQL 에 없다). 논리 가드이므로 동시 적재가 겹치면 중복이 생길 수 있고, 알림 하나가 두 줄 보이는 정도라 감수한다.
- **알림 적재가 채팅 전송 경로에 붙는다.** 브로드캐스트 뒤에 두어 전달 지연은 없지만, 메시지마다 삭제+삽입이 한 번 일어난다. 방 인원이 최대 5명이라 현재 규모에서는 문제가 아니다 — 방이 커지면 큐로 뺀다.
- **알림 토글(`member_notification_setting`)은 센터를 막지 않는다.** 토글은 푸시 수신 동의다. 푸시가 붙을 때 그 게이트로 쓰인다.
- **개인정보가 알림 본문에 들어간다**(닉네임·메시지 미리보기). 30일 purge 와 탈퇴 완전 삭제(`LeftMemberPurgeService`)가 그 대가를 치른다.
