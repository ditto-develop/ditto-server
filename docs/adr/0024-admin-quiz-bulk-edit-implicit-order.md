# ADR 0024 — 어드민 문항 편집은 폼 한 번으로 저장하고, 순서는 화면 순서로 매긴다

- 상태: Accepted (2026-09-10)
- 근거: 어드민 사용성 문제 제기 + 기존 화면 실측(제출 31회)

## Context

퀴즈셋 하나(문항 10개, 선택지 2개씩)를 만들려면 폼 제출이 31번 필요했다. 퀴즈셋 생성 1번, 문항 추가 10번,
선택지 추가 20번. 매번 전체 페이지가 다시 뜨고 스크롤이 맨 위로 돌아가, 방금 추가한 문항 카드를 찾아 다시 내려가야 했다.

`displayOrder`는 `detail.html`의 문항 추가·선택지 추가 폼 기본값이 둘 다 `value="1"`이라, 그대로 두면 문항 10개가
전부 순서 1이 됐다. 서버가 계산할 수 있는 값을 화면이 사용자에게 물었다.

문항 카드 하나에 폼이 4종류(문항 수정 / 문항 삭제 / 선택지별 수정·삭제 / 선택지 추가)라 문항 10개면 폼이 50개 넘게 렌더됐다.

## Decision

문항 전체를 퀴즈셋 폼에 실어 **저장 한 번**으로 반영한다.

- **순서는 받지 않는다.** `displayOrder`는 `quizzes[i]`의 `i+1`로 서버가 넣고, 선택지는 좌 1 · 우 2로 고정한다.
  화면에 보이는 위에서 아래 순서가 곧 저장 순서다. 순서 변경은 드래그와 ▲▼로 하고, 제출 직전 JS가 `name`을
  `quizzes[i].*`로 다시 매긴다.
- **선택지는 문항당 2개.** 추가·삭제 버튼 없이 `⇄`로 좌우만 맞바꾼다. 맞바꿈은 값 교환이 아니라 두 행의 순서 교환이라
  `choice_id`가 그대로 남는다.
- **생성 화면도 한 장.** 새 퀴즈셋은 정보와 문항을 `POST /admin/quiz-sets` 한 번으로 만든다. 제출 31회 → 1회.
- **기존 행 판별은 id hidden.** 값이 있으면 update, 비면 insert, 제출에 없는 기존 id는 delete. 질문만 고쳐도
  `quiz_id`가 유지된다.
- **제출된 행은 모두 채워져 있어야 한다.** 빈 행은 저장을 거부한다. 규칙을 하나로 두면 "빈 행이 곧 삭제"라는
  숨은 경로가 생기지 않는다. 화면 기본 빈 행은 제출 직전 JS가 걷어내되, `id`가 실린 행은 손대지 않는다.
  삭제는 `문항 삭제` 버튼(= id를 아예 안 보냄) 한 경로로만 남는다.
- **답변이 달린 문항은 지우지 못한다.** 선택지 수 변경도 막고(늘리는 쪽까지) 문구 수정만 허용한다.
- **참여가 시작된 퀴즈셋은 문항 개수를 바꿀 수 없다.** `quiz_progress.totalCount`가 첫 답변 시점의
  `countByQuizSetId`로 굳고 `val`이라 다시 계산되지 않는다(`QuizProgress.kt:39`, `QuizProgressService.kt:235`).
  문항이 줄면 이미 시작한 회원은 `answeredCount >= totalCount`에 닿지 못해 완주할 수 없고, 그 주 매칭 후보에서 빠진다.
- **`quizzes`가 비면 문항을 건드리지 않는다.**
- **같은 문항 id를 두 번 보내면 거부한다.** 뒷 행이 앞 행 수정을 덮어써 조용히 한 행이 사라지는 것을 막는다.

전량 삭제 후 재삽입은 쓸 수 없다. `quiz_answer`가 `quiz_id`·`choice_id`를 FK 없이 참조하고
`MatchScoreCalculator`가 그 짝의 일치로 점수를 내므로, 재삽입하면 DB 오류 없이 기존 답변이 매칭에서 조용히 빠진다.

## Consequences

- 얻음: 퀴즈셋 하나를 만드는 제출이 31회에서 1회로 줄었다. 순서를 손으로 세는 일이 없어졌고, 개별 POST 6개와
  서비스 메서드 6개, 문항 카드별 폼 4종이 사라졌다.
- 비용: 순서가 DOM 순서에 의존하므로 JS 없이는 순서 변경이 안 된다. `name` 재부여가 깨져 인덱스에 빈칸이 생기면
  Spring은 그 자리를 `null`이 아니라 빈 `QuizForm`으로 채운다(`growCollectionIfNecessary`). 뒤 행을 버리지는 않지만
  빈 행이 섞여 저장이 거부된다.
- 검증 실패는 리다이렉트하지 않고 폼을 그대로 다시 그린다. 문항 열 개를 채운 뒤 한 칸 실수로 전부 다시 입력하게
  만들지 않으려는 것이다. `GlobalExceptionHandler`는 `basePackages` 제한 없는 `@RestControllerAdvice`라
  어드민 `@Controller`에도 걸려, 그대로 두면 브라우저에 JSON이 200으로 찍히고 입력이 사라진다.
- **문항 전체 삭제는 지원하지 않는다.** `quizzes`가 빈 제출을 "변경 없음"으로 읽기 때문이다. 실수로 파라미터가
  누락된 요청이 문항을 지우는 사고를 막는 쪽을 택했다. 전부 지우려면 퀴즈셋을 삭제한다.
- 선택지가 3개 이상인 기존 문항은 화면이 그 개수만큼 렌더한다. 2칸만 보여주면 3번째가 조용히 삭제되기 때문이다.
  반대로 개별 추가 UI 시절에 생긴 선택지 2개 미만 문항은 렌더 시 빈 칸을 2개까지 채워 준다. 채우지 않으면
  화면에 추가 버튼이 없어 그 퀴즈셋을 영구히 저장할 수 없다.
- 답변이 달린 문항의 문구는 고칠 수 있다. `choice_id`가 유지되므로 답변이 살아 있고, 오타 수정을 막을 이유가 없다.
