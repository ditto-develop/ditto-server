# ADR 0013 — 재매칭 중복은 성사 시점이 아니라 방 생성 시점에서 막는다

- 상태: Accepted
- 근거: Issue #112, 기획 확인(2026-07-27), 대안 검토(2026-07-29)

## Context

같은 두 사람이 한 주에 서로 다른 그룹에서 함께 만날 수 있다. 이 프로젝트는 그것을 허용하도록 설계돼 있다 — 한 주에 퀴즈셋이 여러 개일 수 있고, `GroupMatch`의 `quizSetId` 유일키를 제거해 퀴즈셋당 여러 그룹을 허용하며, `GroupMatchMember` 유일키가 `(room_id, member_id)`라 한 멤버가 여러 그룹에 참여할 수 있다([ADR 0008](0008-matching-entity-uniqueness-modeling.md)).

그래서 A와 B가 그룹 #1과 그룹 #2에서 모두 만나고, 양쪽 평가에서 서로를 선택하면 `rematch` 행 두 개가 각각 `MATCHED`가 된다. `rematch` 유일키는 `(source_group_match_id, member_id_1, member_id_2)`로 **소스 그룹 단위**라 이를 막지 않는다 — 실제로 다른 만남에서 나온 다른 의사이므로 두 행이 존재하는 것 자체는 옳다.

문제는 결과물이다. 두 성사가 같은 주말로 향하면 같은 쌍의 채팅방이 두 개 열리고, 두 사람이 서로 다른 방에 말을 걸어 **상대가 응답하지 않는다고 오해**할 수 있다. `chat_room` 유일키는 `(room_type, source_id)`이고 `source_id`가 `rematch.id`라 DB는 두 방을 정상으로 받아들인다.

기획 확인 결과 횟수 제한은 없다(2026-07-27) — 한 주에 여러 명과 성사 가능하고, 같은 상대와 다른 주말에 다시 성사되는 것도 허용한다. 막아야 하는 것은 **같은 쌍·같은 기간에 방이 둘 열리는 중복** 하나다.

## Decision

중복은 **방을 만드는 시점(`I2`)에서** 막는다. 성사 판정 트랜잭션은 중복을 신경 쓰지 않고, 두 `rematch` 행 모두 `MATCHED`로 남긴다.

`I2`가 지켜야 할 것:

1. 이번 기간에 성사된 재매칭으로 방을 만들 때, **같은 쌍의 방을 이미 만들었으면 건너뛴다.** 두 성사는 하나의 방을 공유한다.
2. `A3`(재매칭 결과 조회)는 성사 2건을 그대로 반환하고 `chatRoomId`를 같은 값으로 채운다. 두 그룹에서 모두 성사된 것은 사실이고, dedup 규칙을 조회 경로에 다시 심지 않는다.
3. 개방 시각이 지났고 종료 전이면 즉시 개방한다. 주말 진행 중에 확정된 성사(⑧-1: 그 주말에 합류)와 스케줄러 지연·운영 복구를 함께 커버한다.
4. 채팅 기간(개방·종료 시각) 계산은 `I2`가 단일 책임진다. `rematch`는 채팅 시각을 저장하지 않으며([ADR 0012](0012-rematch-as-separate-table.md)) SSOT는 `chat_room.opens_at`/`expires_at`(`C1`)이다.

`I2`는 단일 스케줄러이므로 순차 처리된다 — 중복 판정에 잠금·유일키 같은 동시성 장치가 필요하지 않다. 다중 인스턴스로 확장하면 스케줄러 잠금이 필요해지는데, 이는 기존 매칭 스케줄러와 같은 문제이므로 그때 함께 다룬다.

## 검토했으나 채택하지 않은 대안

**① 성사 시점에 별도 slot 테이블로 확보** (`rematch_slot`, UK `(chat_opens_on, member_id_1, member_id_2)`). 성사 즉시 판정해 잘못된 성사 통보를 막는 장점이 있으나, 이 트랙에서 필요한 유일한 역할이 "유일키 보유"였고 그 대가로 테이블·엔티티·리포지토리·마이그레이션이 늘었다. 결정적으로 확보 실패를 `save()`의 유일키 위반 예외로 판정할 수 없다 — 제약 위반 예외가 나면 Spring이 참여 트랜잭션을 롤백 전용으로 마킹해 같은 트랜잭션의 취소 전이가 커밋되지 못하고, 제출 결과까지 유실된 채 재시도가 같은 경로를 반복하는 고착이 된다. 이를 피하려면 `INSERT IGNORE` + 영향 행 수 판정과 H2 `MODE=MySQL`이 필요했다. 중복 방지 하나에 비해 기계 장치가 과했다.

**② `rematch`에 nullable 컬럼 + 유일키** (`chat_opens_on DATE NULL` + UK `(chat_opens_on, member_id_1, member_id_2)`). MySQL이 유일 인덱스에서 NULL을 서로 다른 값으로 취급하므로 조건부 유일성을 흉내낼 수 있다(테이블이 늘지 않는다). 그러나 확보 판정을 즉시 받으려면 **엔티티로 수정 중인 바로 그 행**에 native `UPDATE IGNORE`를 해야 하고, Hibernate가 flush 때 전체 컬럼을 UPDATE하므로 native로 채운 값을 낡은 엔티티 값으로 덮어쓴다. `@DynamicUpdate`를 붙이거나 성사 로직을 SQL로 내려야 하는데 후자는 `submitWants`에 모아둔 도메인 로직을 해체한다. 또 `rematch`가 채팅 시각을 저장하지 않는다는 [ADR 0012](0012-rematch-as-separate-table.md) 결정과 충돌하고, NULL 트릭은 스키마만 봐서는 알 수 없다.

**③ 방을 둘 다 만들고 읽을 때 하나만 노출.** 규칙이 모든 읽기 경로(방 목록·상세·전송 검증·STOMP 구독 인가·`A3`)로 퍼지고, 두 사용자가 같은 방을 고르도록 결정적 규칙(`min(roomId)` 등)을 공유해야 하며, 숨긴 방도 멤버십 인가는 통과하므로 아무도 보지 못하는 곳에 메시지가 쌓인다. "만들고 숨기기"보다 "안 만들기"가 지켜야 할 곳이 한 곳뿐이다.

## Consequences

- 얻음: 중복 방지에 새 테이블·컬럼·동시성 장치가 필요 없다. 두 성사가 모두 `MATCHED`로 남아 "두 그룹에서 서로를 원했다"는 사실이 보존된다. `Rematch`의 취소 사유는 `NOT_MUTUAL` 하나뿐이라 [ADR 0012](0012-rematch-as-separate-table.md)의 "`cancel_reason` 컬럼을 두지 않는다" 결정이 그대로 유지된다.
- 비용: 성사 응답과 실제 개방 사이에 어긋남이 생길 수 있다 — 사용자는 두 성사를 통보받지만 방은 하나만 열린다. 성사 자체가 취소되는 것은 아니므로 통보가 거짓이 되지는 않으나, `A3`가 두 성사에 같은 `chatRoomId`를 반환하는 표현을 FE와 맞춰야 한다.
- 중복 판정이 `I2` 구현 전까지 존재하지 않는다. 그 사이에 재매칭 채팅이 열리는 경로 자체가 없으므로(방을 만드는 것이 `I2`다) 노출되는 위험은 없다.
- 운영 중 대화 분산이 실제로 문제가 되면 대안 ①로 승격할 수 있다. slot은 insert-only라 과거 데이터 백필이 필요 없고 그 시점부터 쌓으면 된다.
