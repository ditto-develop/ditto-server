# ADR 0032 — 닉네임을 확인 시점에 10분 예약하고, 프로필 수정 변경을 2회/14일로 묶는다

- 상태: Accepted
- 근거: QA 수정사항(2026-09-27) "A·B가 동시에 가입 중일 때 A가 먼저 닉네임을 고르면 B가 선점하지 못하게", "닉네임 수정은 2회, 소진 시 14일 제한, 채팅방이 살아 있으면 불가"

## Context

닉네임은 `member_unique_1`이 막고 있어 두 사람이 같은 닉네임으로 **저장**될 수는 없었다. 그러나 선점 시점이 저장(가입 버튼)이라, 온보딩에서 중복 확인을 통과한 사람이 입력을 마치는 사이 다른 사람이 같은 닉네임으로 먼저 가입하면 앞 사람은 마지막 단계에서 막혔다. 게다가 동시 저장은 유니크 위반이 번역되지 않아 9999(서버 오류)로 나갔다. 중복 확인 API(v1)는 API Key 만 받아 **누가** 확인했는지 모른다.

## Decision

- **확인 = 예약.** `GET /api/v2/users/nickname/availability?nickname=`(JWT)가 사용 가능하면 그 자리에서 10분 동안 내게 예약한다(`nickname_reservation`, 닉네임·회원 각각 유니크). v1 은 그대로 두되 남의 유효한 예약도 "사용 불가"로 본다.
  - 경로를 v2 로 새로 낸 이유: v1 은 비회원 경로라 호출자를 모른다. v1 을 JWT 로 옮기면 기존 호출이 깨진다.
  - 쿼리 파라미터인 이유: PENDING 허용 목록(`SecurityConfig.PENDING_ALLOWED_PATHS`)이 경로 완전 일치다. 경로 변수를 쓰려면 필터의 매칭 방식을 바꿔야 해서 보안 표면이 넓어진다.
  - 동시 첫 예약은 유니크 제약이 한쪽을 막고, 진 쪽은 트랜잭션 밖(파사드)에서 `available=false`로 바꾼다(`MemberDeviceFacade`와 같은 방식).
  - 만료된 예약은 청소하지 않고 다음 예약이 덮는다. 실제 시각으로 잰다.
- **저장 경로의 최종 방어는 유니크 제약 그대로.** 가입·프로필 수정은 남의 예약을 3003 으로 거부하고, 그래도 겹친 동시 저장은 `GlobalExceptionHandler`가 `member_unique_1` 위반을 3003 으로 번역한다.
- **변경 제한은 이력 테이블이 아니라 회원 컬럼 두 개**(`nickname_change_count`, `nickname_change_locked_until`). 규칙이 "현재 창의 횟수"만 보므로 과거 내역이 필요 없다. 2회째 변경 시각부터 14일 잠그고, 잠금이 풀린 뒤 첫 변경에서 횟수를 초기화한다.
- **끝나지 않은 채팅방이 있으면 변경 불가.** 탈퇴 검사와 같은 `existsUnendedRoomOfMember`(예약·진행, 모든 방 유형, 내가 나간 방 제외)를 쓴다.

## Consequences

- FE 온보딩은 v2 로 바꿔야 예약 효과가 난다. v1 을 계속 부르면 기존처럼 저장 시점에만 막힌다.
- 한 회원이 닉네임을 계속 바꿔 가며 확인하면 매번 이전 예약이 풀린다 — 회원당 1건이라 남의 닉네임을 쓸어 담을 수 없다.
- 예약을 확인만 하고 가입하지 않으면 그 닉네임은 최대 10분 동안 남이 못 쓴다. 감수한다.
- 성사된 재매칭인데 방이 아직 없는 1분 창(탈퇴 검사의 세 번째 조건)은 변경 제한에 넣지 않았다. 방이 곧 생기고, 이름이 바뀌어도 대화가 시작되기 전이다.
