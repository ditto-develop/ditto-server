# ADR 0043 — 채팅 본문은 서버에서 암호화해 저장하고 종단간 암호화는 미룬다

- 상태: Accepted (2026-10-17)
- 근거: discussion (#314)

## Context

채팅 본문(`chat_message.content`)이 평문으로 저장돼 있었다. 개인정보 보호 차원에서 저장 시 암호화가 필요했다.

두 가지를 비교했다.

- 서버 컬럼 암호화: 저장할 때 서버가 암호화하고 읽을 때 복호화한다. DB 덤프·백업이 새도 내용이 드러나지 않는다. 서버는 여전히 내용을 읽는다.
- 종단간 암호화(E2E): 기기에서 암호화하고 받는 기기에서만 푼다. 운영자도 읽지 못한다. 대신 기기별 키 관리·그룹 이탈 시 키 교체·기기 변경 시 키 백업·푸시 미리보기 복호화를 앱이 맡아야 하고, 신고가 들어와도 운영자가 원문을 확인할 수 없다. 지금 앱은 화면 코드를 서버에서 받아 실행하는 구조라, 배포 권한만 있으면 키를 꺼내는 코드를 내보낼 수 있어 E2E 의 보장이 약하다.

## Decision

서버 컬럼 암호화를 쓴다. E2E 는 앱이 암호화 코드를 앱 번들에 담는 구조가 될 때 다시 판단한다.

- AES-256-GCM, 메시지마다 무작위 IV. 저장 형식은 `enc:v1:` + Base64(IV + 암호문 + 태그)다.
- JPA 컨버터(`ChatContentConverter`)가 저장·조회 때 바꾼다. 서비스·DTO·STOMP 는 평문을 그대로 다룬다.
- 기존 평문 행은 옮기지 않는다. 접두어가 없으면 평문으로 보고 그대로 읽는다.
- 유형(TEXT·IMAGE·SYSTEM)을 가리지 않고 모두 암호화한다. 컨버터는 다른 컬럼을 볼 수 없고, 본문으로 검색하는 쿼리가 없다.
- 키는 Secrets Manager(`CHAT_CONTENT_ENCRYPTION_KEY`, Base64 32바이트)에서 받는다. 없거나 길이가 틀리면 앱이 뜨지 않는다.
- 운영 콘솔의 채팅방 화면은 더미가 들어 있던 방만 연다. 서버가 복호화해서 보여 주므로 열람 범위를 코드로 막아야 한다.

## Consequences

- 얻음: DB 만 새는 경우 본문이 드러나지 않는다. E2E 로 넘어가도 컬럼 확장·형식 접두어·과도기 평문 처리는 그대로 쓴다.
- 비용: 키를 잃으면 암호화된 메시지를 되살릴 수 없다. 키를 바꾸려면 `enc:v2:` 접두어와 옛 키 복호화 경로를 추가해야 한다.
- 비용: 컬럼이 `VARCHAR(4100)`으로 넓어졌다. 입력 상한 1000자는 그대로다.
- 비용: 알림 센터(`notification.body`)의 메시지 미리보기와 암호화 전에 쌓인 행은 평문으로 남는다. 필요해지면 따로 옮긴다.
